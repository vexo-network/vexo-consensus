## Бэкенд Pebble и бинарные записи

Бэкенд по умолчанию — Pebble (`github.com/cockroachdb/pebble/v2`), открываемый с кешем блоков 256 MiB и memtable по 64 MiB. Записи хранятся в каноническом бинарном кодировании пакета `types`: минимальные uvarint, байтовые строки и списки с префиксом длины, хеши как их 32 байта, необязательное значение после байта присутствия `0` или `1`, поля в порядке объявляющей их структуры. Декодер отвергает всё остальное, включая лишние байты в конце, поэтому повреждённая запись сообщается как ошибка, а не читается как другое значение; у каждой записи одно кодирование. Каталог данных, записанный более ранней сборкой (LevelDB, записи JSON), нечитаем и не конвертируется: Pebble отказывается открывать его с ошибкой `format major version 1`. Такой узел восстановите из snapshot или синхронизируйте в пустой каталог данных.

Связанные идентификаторы:

- `pebble: database "<dir>" was written in format major version 1, which is no longer supported`

## История состояния (undo log) и кеш дерева

История состояния — это undo log версий по ключам. Когда ключ меняется на высоте (записи блока на его высоте, прямая запись (`Set`, `Delete`, `SetBatch`) после первого зафиксированного состояния на следующей зафиксированной высоте), store записывает значение, которое ключ имел до этого, включая отсутствие, как версию ключа на этой высоте, один раз на ключ и высоту; прямые записи до блока, фиксирующего их высоту, сохраняют версию, записанную первой из них (`hdirect` указывает эту высоту). Значение ключа на зафиксированной высоте — это значение, записанное его самой низкой версией выше этой высоты, а если такой нет — текущее значение. Запись изменения читает только текущее значение ключа, а не историю, и историческое чтение — один seek по версиям ключа. `PruneBelow` удаляет все версии на высоте, начиная с которой он хранит, и ниже. Узлы дерева версионируются так же. Две структуры в памяти уменьшают работу с деревом на блок; ни одна не сохраняется на диск и не меняет результат: кеш узлов дерева до 2^18 закодированных узлов текущих деревьев (его обновляет каждый batch store, а generation, нечётная во время фиксации такого batch, позволяет читателю использовать кеш только в состоянии своего snapshot), и для каждого namespace корень и изменения узлов последнего вычисления корня, с ключом из этой generation и SHA-256 digest записей namespace, так что app hash, state roots и commit вычисляют одни и те же записи один раз.

## Компактация WAL мемпула и batch генезиса

Commit компактирует WAL мемпула, только когда тот содержит не меньше 4 MiB и вдвое больше, чем после последней компактации или открытия. Поэтому каждый дописанный байт в среднем переписывается примерно один раз, а журнал, который воспроизводит перезапуск, остаётся в пределах удвоенного живого содержимого или 4 MiB. Явная компактация (`Node.Compact` или запуск, отбрасывающий воспроизведённые транзакции, которые отклоняет приложение) переписывает его всегда. `InitChain` записывает состояние генезиса всех модулей одним batch, поэтому генезис со множеством счетов стоит одной долговременной записи, а неудавшийся генезис ничего не оставляет в store.

## Finality proofs в batch коммита и отложенное удаление из mempool

Путь коммита узла записывает finality proofs, которые завершает QC блока, в тот же batch block/state/app-write (`CommitBlockStateWithWrites` получает их последним аргументом). Поэтому коммит стоит одной durable-записи, а не ещё одной на каждый proof. Proof, который store отверг бы, не попадает в batch: его сохраняет шаг после коммита и сообщает об ошибке. Коммит удаляет свои транзакции из pool и ставит запись об удалении в очередь, не дожидаясь её sync. Следующий коммит ждёт, пока эта запись станет durable, прежде чем выполнить свой блок, так как перезапуск повторяет удаление только для последнего закоммиченного блока. Обычно запись разделяет sync последующей admission.

## Отложенное хеширование state tree

Вычисление state tree откладывает хеширование: write помечает изменённые им половины, а каждый изменённый node хешируется один раз, снизу вверх, когда запрашивают root, proof или изменения. Поэтому nodes около root, которые переписывает каждый write блока, хешируются один раз на блок, а не на каждый write. Хеши, nodes и roots те же, что при хешировании после каждого write.

## Периодический sync mempool WAL

Mempool WAL записывает каждое изменение в log и синхронизирует его каждые 100 ms (`walSyncInterval`). Admission ждёт записи, а не sync. Сбой процесса сохраняет каждую запись; сбой машины теряет не больше admissions последнего интервала, которые клиенты отправляют снова. Запись об удалении закоммиченного блока синхронизируется до следующего коммита (`WaitDurable`).
