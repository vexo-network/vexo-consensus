# Добавляем валидатор

В этом руководстве описан процесс добавления валидатора в сеть Vexo оператором.

Точный путь допуска зависит от политики ставок и управления сетью. Как минимум, валидатор должен быть представлен в состоянии цепочки, иметь действительные учетные данные и стать частью обновления набора валидаторов с версионированием по высоте.

## 1. Инициализация домашней страницы валидатора
```bash
vexod init validator \
  --home .vexo-validator-new \
  --chain-id vexo-chain \
  --validator validator-new \
  --encrypt-keys
```
Для ключа валидатора BLS:
```bash
vexod init validator \
  --home .vexo-validator-new \
  --chain-id vexo-chain \
  --validator validator-new \
  --key-type bls \
  --encrypt-keys
```
Установите `VEXO_KEY_PASSPHRASE` перед выполнением этих команд или передайте `--passphrase` для одноразовой локальной настройки.

При включении валидатора BLS в существующую цепочку включите сгенерированные метаданные `bls_pop` в предложение по обновлению валидатора.
Путь ключа BLS по умолчанию использует `blst-bls12381-minpk-v1`; используйте `vexod keys gen --type bls --bls-adapter circl-bls12381-g1sigg2-basic-v1` только для эталонного тестирования/тестирования на совместимость.

Архивируйте сгенерированный открытый ключ:
```bash
vexod keys show --home .vexo-validator-new --json
```
Также сохраните сгенерированный `node.key.json`. Он подписывает P2P-рукопожатия для `network_config.json:p2p.node_id`; это не консенсусный ключ валидатора, и его не следует повторно использовать в качестве ключа учетной записи.

## 2. Настройка сетевых адресов и узлов

Отредактируйте `.vexo-validator-new/network_config.json` и установите локальные адреса прослушивания плюс постоянные узлы:
```json
{
  "schema_version": "v1",
  "rpc": {
    "enabled": true,
    "address": "0.0.0.0:26657"
  },
  "p2p": {
    "enabled": true,
    "node_id": "validator-new",
    "node_key_path": "node.key.json",
    "listen_address": "0.0.0.0:26656",
    "peers": {
      "validator-1": "validator-1.example.com:26656",
      "validator-2": "validator-2.example.com:26656",
      "validator-3": "validator-3.example.com:26656"
    }
  },
  "peer_scoring": {
    "InitialScore": 100,
    "MaxScore": 1000,
    "BanThreshold": 0
  }
}
```
Не полагайтесь на долговременные переопределения сетевых команд командной строки для рабочих валидаторов. Сохраняйте постоянные адреса одноранговых узлов в `network_config.json`.

Используйте отдельные роли адресов:

- `p2p.listen_address` и `rpc.address` — это локальные адреса привязки для этого компьютера или контейнера.
- `p2p.node_id` — это идентификатор узла этого узла. Поддерживайте его стабильность после того, как его усвоят сверстники.
- `p2p.node_key_path` указывает на локальный ключ подписи квитирования для этого однорангового идентификатора.
- `p2p.peers` содержит цели набора, которые этот узел использует для связи с другими узлами; ключи карты должны быть значениями `p2p.node_id` удаленных узлов.
- Метаданные валидатора `p2p_address` и `rpc_address` должны содержать общедоступные рекламируемые адреса, а не имена служб, предназначенных только для Docker, если только сеть не является намеренно частной.

## 3. Отправьте допуск валидатора

Например, потоки ставок, создайте транзакцию ставок:
```bash
vexod staking --help
```
Транзакция допуска валидатора должна включать в себя:

- идентификатор валидатора
- адрес валидатора
- консенсусный открытый ключ
- количество голосов или ссылка на долю
- базисные баллы комиссии валидатора, если цепочка позволяет самостоятельно обновлять комиссию
- Метаданные P2P `node_id`, если цепочка использует метаданные генезиса/валидатора для предварительного заполнения карт узлов.
- метаданные общедоступного P2P-адреса
- публичные метаданные адреса RPC, если они общедоступны
- Метаданные подтверждения владения BLS, когда BLS включен.

Обновление валидатора должно вступить в силу на определенной высоте и создать новый хэш набора валидаторов.

После того, как валидатор активен, операторы могут раскрывать состояние вознаграждения через модуль ставок:
```bash
vexod staking query commission validator-1
vexod staking query rewards alice validator-1
```
## 4. Проверьте обновление набора валидаторов

После обновления высоты:
```bash
curl http://127.0.0.1:26657/v1/validators/<height>
```
Проверьте:

- валидатор появляется в наборе, специфичном для высоты
- количество голосов правильное
- хеш набора валидаторов изменен, как и ожидалось
- доказательства окончательности ссылаются на правильную высоту набора валидаторов

## 5. Ротация ключей валидатора плана

Ключи валидатора можно чередовать, подготовив следующий ключевой документ с непересекающимися метаданными `active_from` и `active_until`, а затем запустив узел с дополнительным ключом ротации:
```bash
vexod keys gen --home .vexo-validator-new --path next-validator.key.json --id key-2 --active-from 1001
vexod keys rotation-plan --home .vexo-validator-new --key validator.key.json --key next-validator.key.json
vexod start --home .vexo-validator-new --rotation-key next-validator.key.json --dry-run
```
Во время подписания узел использует ключ, активное окно которого содержит консенсусную высоту. Ключевые документы удаленной подписывающей стороны придерживаются той же политики, токена аутентификации и требований к защите двойной подписи.

## 6. Запустить валидатор
```bash
vexod config audit --home .vexo-validator-new --strict
vexod start --home .vexo-validator-new
```
В автозагрузке нет переключателя режима сети. Используйте `config audit --strict` перед запуском, если ожидается, что сеть будет соответствовать предположениям о безопасности общедоступной сети.

## 7. Монитор

Смотреть:

- задержка предложения/голосования
- таймауты раундов
- сбои подписи валидатора
- одноранговые баны
- размер мемпула
- фиксировать задержку
- состояние моментального снимка/воспроизведения

Использование:
```bash
vexod ops thresholds --json
vexod ops incident --metrics-file current.json --previous-metrics-file previous.json --window 1m
```
## Примечания по безопасности

- Никогда не используйте повторно ключи валидатора в независимых цепочках.
— Оставьте политику удаленной подписи включенной для производственных валидаторов.
- Не допускайте валидатора BLS без доказательства владения или эквивалентной защиты от мошеннического ключа.
- Не сокращайте и не заключайте в тюрьму валидатор без проверенных доказательств, привязанных к правильному набору валидаторов высоты доказательства.
