## Модель

Vexo использует ядро BFT в стиле HotStuff с предложениями, голосами, сертификатами кворума, сертификатами тайм-аута, безопасностью с заблокированным контролем качества и окончательностью с тремя цепочками.

За блок можно безопасно голосовать только в том случае, если он расширяет заблокированный контроль качества или содержит выравнивающий контроль качества, по крайней мере, такой же новый, как и блокировка. Блок становится финализированным, когда правило трех цепочек доказывает безопасное расширение родительской/прародительской цепочки.

Реализация связывает решение трех цепочек с явными высотами блока, родительского элемента и родительского элемента. Контроль качества блока должен сертифицировать высоту/хеш родительского элемента, а контроль качества родительского блока должен сертифицировать высоту/хэш родительского элемента; Синтетические или пропущенные по высоте цепочки контроля качества отклоняются до регистрации решения об окончательности.

## Условия исполнения

Vexo постоянно использует эти термины:

- **Сертифицировано QC**: блок имеет достаточно голосов для формирования сертификата кворума.
- **Завершено**: правило трех цепочек HotStuff завершает родительский блок.
- **Выполнено**: приложение выполнило `FinalizeBlock` для блока.
- **Состояние зафиксировано**: записи KV приложения, запись блока, запись состояния и корни состояния модуля были надежно зафиксированы.

Путь выполнения узла использует две отдельные границы:

- **Граница фиксации выполнения**: блок, сертифицированный QC, может быть выполнен и атомарно сохранен при записи приложения + запись блока + запись состояния + корни состояния.
- **Граница окончательности консенсуса**: правило трех цепочек финализирует предка и является единственным источником доказательств окончательности легкого клиента.

`consensus_config.json` предоставляет этот выбор через `execution_commit`. Сгенерированные дома валидаторов по умолчанию имеют значение `finalized`, который выполняет только предка, выбранного правилом окончательности трех цепочек, поэтому фиксации состояния соответствуют более строгой границе окончательности. Граница `qc` с меньшей задержкой остается доступной для пользовательских развертываний, но `require_network_safety` отклоняет ее. Операторы и пользователи SDK должны рассматривать журналы `block_committed` как события фиксации состояния для настроенной границы выполнения. Доказательства окончательности описывают согласованную окончательность на высоте, установленной валидатором.

## Граница безопасности

Безопасность зависит от:

- менее одной трети византийского права голоса
- разделенные по домену подписи предложения, голосования, таймаута-голосования и окончательности
- привязка хеша, установленного валидатором, на соответствующей высоте доказательства
- уникальные известные подписавшие стороны в QC и доказательствах окончательности
- достоверные доказательства двусмысленности валидатора
- отказ от противоречивых решений коммита на одной и той же финальной высоте

## Граница криптовалюты

- `deterministic` предназначен только для тестирования и не проходит проверку безопасности сети.
- `ed25519` поддерживается для тестирования общедоступной сети и подготовки к запуску.
- `bls` по умолчанию имеет значение `blst-bls12381-minpk-v1` и требует подтверждения владения или эквивалентной защиты от мошеннических ключей, проверок подгрупп, проверки открытого ключа, доказательств аудита зависимостей и доказательств выпуска. Встроенный адаптер CIRCL остается эталонной интеграцией для интерфейса среды выполнения и не является отказом от производственной безопасности.
- Для проверки безопасности сети требуются метаданные адаптера VRF для выбора комитета VRF. Встроенный адаптер ECVRF может удовлетворить интерфейс времени выполнения; детерминированный VRF остается только для тестирования и не должен использоваться для сетей, несущих ценность.

## Операционная граница

Код включает в себя проверки, ориентированные на производство, но для общедоступных развертываний по-прежнему требуется:

- строгий аудит конфигурации для каждого дома валидатора
- доказательства освобождения ворот
- внешняя проверка безопасности
- свидетельства долгосрочного существования и хаоса с несколькими хостами
- подтверждение политики подписывающего лица/KMS
- обзор экономической и управленческой политики конкретной сети

Прежде чем рассматривать выпуск как готовый к производству, просмотрите [Готовность аудита безопасности](./security/audit-readiness.md) и [Конвейер выпуска](./release/release-pipeline.md).
